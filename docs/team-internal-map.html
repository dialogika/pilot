Detail Per Halaman — Data Masuk & Keluar

Untuk tiap halaman: koleksi mana yang ditampilkan (dibaca) dan koleksi mana yang disimpan input-nya (ditulis). Pakai ini saat mau menambah field/tampilan: cek dulu halaman ini sudah baca/tulis ke mana, supaya tidak bikin koleksi dobel.

Cara baca: 📥 READ = data yang dimunculkan di halaman (ambil dari sini) · 📤 WRITE = tujuan simpan input (form/tombol simpan menulis ke sini) · (sub) = subkoleksi di bawah dokumen (mis. projects/{id}/lists).

Data Hygiene — Titik Rawan Penumpukan

Temuan dari scan kode. Ini yang paling mungkin bikin data berantakan / dobel. Rekomendasi: standarkan sebelum menambah fitur baru.

1. Koleksi kembar (singular vs plural). Kode memakai keduanya secara campur — sumber utama duplikasi:
positionsposition departmentsdepartment mentormentors team_managementteams
→ Pilih satu bentuk kanonik per entitas, migrasikan, lalu hapus yang lain.
2. Field boolean redundan di projects. Ditemukan is_pinned DAN pinned ditulis bersamaan dengan nilai sama. Cukup satu.
3. Dua sumber kebenaran untuk Project/Task. Data ditulis ke Firestore dan di-mirror ke Google Sheets via Apps Script (appscript.js). Rawan tidak sinkron. Tentukan mana yang jadi source of truth (disarankan Firestore) dan jadikan Sheets read-only/ekspor saja.
4. API key berbeda dari yang kamu berikan. Kode di repo memakai AIzaSyDyzzEYbJkkl-N8snrQf14qvj8De4YliV0 (project pre-dialogika), sedangkan key yang kamu kirim AIzaSyBaO-…nDuG0 berbeda. Pastikan sebelum deploy: apakah pindah project, atau salah satu key sudah tidak dipakai? (Detail di catatan markdown.)
5. Field task tersimpan sebagai string kosong, bukan null. assign_to, due_date, start_date default "". Query "yang belum di-assign" jadi tidak konsisten. Standarkan null/empty.
Yang sudah rapi: struktur subkoleksi projects konsisten dan bersih; auth-guard terpusat di satu file; komponen UI di element/*.js sudah reusable. Pertahankan pola ini.
